# Rust Mixin 最终目标

本文定义项目范围和验收条件。 [架构](ARCHITECTURE.md) · [验证入口](VALIDATION.md)

## 项目愿景

让愿意支持模组的 Rust 游戏接入 Rust Mixin 后，即使游戏开发者没有在某段逻辑上预先添加 Hook，模组作者也能用普通 Rust 函数和属性选择这段逻辑中的位置，并在游戏加载模组时改变其行为。

Hook 指游戏开发者事先安排好的回调位置。例如在伤害计算结束时专门调用一次模组函数。Rust Mixin 希望让游戏开发者一次性接入加载机制，由模组作者在获准修改的组件里挑选目标函数及其内部位置。

Rust Mixin 面向不同的 Rust 游戏。游戏接入时提供自己的组件和目标信息，模组作者复用同一套 SDK、加载器和工具。战斗和掉落只用作验收案例，工具本身可以应用到游戏开发者开放的其他逻辑。

## 生效时机

- **启动加载**。宿主启动时应用玩家选中的模组。
- **运行中切换**。接入 `HotReload` 的单线程宿主可在组件调用之间启用、替换或移除模组。

## 三方的使用方式

- **游戏开发者**接入模组加载器，指定哪些游戏组件允许修改。组件内部无需为每条可修改的规则逐个写回调。
- **模组作者**用 Rust 编写逻辑，描述要改哪个函数、哪个位置，以及如何修改，独立构建可分发的模组包。
- **玩家**把模组包装到已发布的游戏中，由游戏读取并应用。玩家无需安装 Rust 编译器或重新构建游戏可执行文件。

## 核心验收场景

1. 游戏开发者发布一个支持加载模组的游戏。战利品组件包含一段掉落数量计算，源码中没有为该计算单独预留 Hook。
2. 模组作者在游戏发布后编写模组，选择这段计算中的一个原有函数调用，将该调用的结果从 3 改为 4，再独立打包。
3. 玩家用同一份游戏发行包分别验证无模组和有模组的行为，观察到掉落数量分别为 3 和 4。
4. 使用与当前游戏版本兼容、但选错位置的模组时，加载器拒绝应用该补丁，并指出失败的模组、目标和匹配结果。跨版本模组则按发布的兼容规则处理。

战斗组件和独立掉落宿主使用不同的目标名称和逻辑，并由同一套 SDK、加载器和工具验收。

热切换验收在同一进程内依次验证原版、启用模组 A、替换为 B 和恢复原版。尝试加载无效模组时，游戏继续使用上一套有效逻辑。宿主继续持有游戏状态，切换后的模组对后续调用生效。 [验收脚本](../scripts/check-loot-host.ps1)

## 游戏发布方式

冰箱演示默认把组件 bitcode 和校验清单编入 `video-game.exe`，也可选择外置。LLVM 和匹配工具链的 Rust 标准库随游戏单独分发。加载器把组件和玩家选中的模组组合，生成游戏可以调用的机器码。 [演示构建](DEMO.md)

项目的支持范围是主动接入并开放指定组件的 Rust 游戏。模组按对应游戏构建和组件的兼容规则加载。现有发布模型把模组视为可信的原生扩展。
