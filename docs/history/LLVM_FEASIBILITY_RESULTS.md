# rustc / LLVM Mixin 可行性与性能报告

日期：2026-11-20。以下为本机实际运行结果。

当前工作区的验收和基准命令见 [验证记录](../VALIDATION.md)。

## 结论

方案阶段 A 通过：真实 rustc 产物能够保留、识别内部直接调用、由 LLVM 加载和执行。无需自行实现 Rust 的函数体语言。

额外完成了一个小范围变换：把游戏内部一次调用的结果送入独立编译的模组函数，伤害从 16 变成 9.5。原被调函数的独立调用仍为 16；修改不是根据模组 ID 在宿主中预写的行为。

性能证据支持继续探索：该纯数值组件在批量执行时接近正常优化编译结果。频繁跨边界的小调用仍有可测差异，LLVM 的包体、加载和内存成本也确实存在。结果不能外推为整款游戏开销只有某个百分比。

## 实验位置与工具链

独立项目：`experiments/llvm-mixin/`，与根目录演示隔离。

- Windows 11 x64，build 26300。
- Intel Core i7-13620H，10 核、16 线程。
- rustc 1.92.0，commit `ded5c06cf21d2b93bffd5d884aa6e96934ee4234`，其报告 LLVM 21.1.3。
- 官方 LLVM 21.1.3 Windows C API DLL，ORC LLJIT。
- 目标 `x86_64-pc-windows-msvc`、CPU 配置 `x86-64`，没有开启 fast-math。
- AOT：rustc O3、thin LTO、codegen-units=1、panic=abort。
- 保存 bitcode：rustc O3，`-C no-prepopulate-passes`，再由运行时执行 LLVM `default<O3>`。

Rust 自带 LLVM 是其工具链集成版本；这里使用相同版本号的官方 LLVM 并验证实际产物，不宣称两者实现完全相同或任意产物均兼容。完整编译器身份、参数和文件哈希保存在测量 JSON 中。

AOT/JIT 最终优化流水线不完全相同，链接方式和代码布局也不同。比较反映这个具体原型的端到端结果，不能据此单独归因所有差异。

## 做了什么

游戏和模组各自有独立 Rust crate。没有自行解析它们的函数体：

```text
游戏 fixture/src/lib.rs -> rustc -> retained_game.bc
模组 handler/src/lib.rs -> rustc -> retained_mod.bc
                                   ↓
                 LLVM C API 解析、链接、类型与目标检查
                                   ↓
                    定位并修改游戏内部一次调用
                                   ↓
                    LLVM O3 优化 -> ORC 生成机器码
```

模组的真实源码包含结构体、局部借用、辅助函数和条件分支：

```rust
fn bonus_for(value: f64, rule: &Rule) -> f64 {
    if value > rule.threshold { rule.bonus } else { 0.0 }
}

pub extern "C" fn mod_adjust_damage(value: f64) -> f64 {
    let rule = Rule { threshold: 10.0, bonus: 3.0, multiplier: 0.5 };
    let bonus = bonus_for(value, &rule);
    (value + bonus) * rule.multiplier
}
```

这些借用发生在模组自己的 Rust 函数内部，接受 rustc 检查；游戏与模组之间只传 f64。没有宣称支持在任意注入位置跨界借用游戏对象。

变换前后的真实 LLVM 指令可在 `artifacts/` 查看。变换前有原始调用；变换后先执行原调用一次，再调用 `mod_adjust_damage`，后续使用改为新结果。

最终优化 IR 已把模组处理函数内联到目标函数，目标体只剩浮点运算、比较和 select，没有保留这次 handler 调用。这是该例能够接近 AOT 的一个证据，不保证所有模组都能内联。

## 正确性和执行独立性

- 16,502 次 AOT/JIT 结果比较：确定性有限输入、正负零、极小数、极值、Infinity、NaN 分类，以及不同循环次数。
- 非 NaN 逐位比较；NaN 只要求两边均为 NaN，不承诺 payload 一致。
- 基础伤害 16，修改后 9.5，未修改 callee 独立结果 16。
- 2 个自动化测试通过：真实产物加载/变换/执行与错误选择器/签名拒绝；载荷哈希和工具链身份拒绝。
- 格式检查、Release Clippy `-D warnings` 通过。
- 3 个性能测量进程均使用空 PATH，全部正常退出。
- 已复制 exe、LLVM DLL、bitcode 和 manifest 打包，空 PATH 实际执行成功并正常退出。
- 执行阶段不调用 Cargo、rustc、外部链接器；AOT 对照也不是 JIT 的回退路径。

这仍不是无开发环境的全新 Windows 虚拟机兼容测试。

## 持续执行性能

3 个独立进程，每种场景每进程测量 21 对样本，每个样本 1600 万次操作；先预热，成对测量时交替执行 AOT/JIT 顺序。总计 252 对样本。使用 `black_box` 和返回结果比较，防止代码被当作无用计算删除。

下表 ns 列为各进程中位数再取中位数；比值列为各进程的成对比值中位数再取中位数。两者不是同一种统计计算，不能要求直接相除完全一致。

| 场景 | AOT ns/操作 | JIT ns/操作 | JIT/AOT 成对比值 | 各进程比值范围 |
| --- | ---: | ---: | ---: | ---: |
| 基础计算，每次跨函数指针边界 | 0.861 | 0.942 | 1.107 | 1.085～1.109 |
| 基础计算，内部批量循环 | 0.872 | 0.869 | 1.004 | 0.999～1.004 |
| 相同模组逻辑，每次跨边界 | 1.282 | 1.089 | 0.845 | 0.841～0.848 |
| 相同模组逻辑，内部批量循环 | 1.219 | 1.217 | 1.001 | 0.991～1.001 |

这里的一次操作是一次伤害计算，不是整个游戏帧。循环生成输入和累加结果的成本也包含在内。

解释：

1. 基础微小调用的 JIT 路径慢约 8.5%～10.9%，绝对差距约 0.08～0.10 ns/操作。这是这个场景的差异，不是游戏帧率下降比例；两边均有间接函数边界，不能把该差距直接称为“间接调用成本”。
2. 批量场景的进程中位比值约在 1% 以内，没有观察到大幅持续执行损失；这不是所有负载的 1% 上界或统计置信区间。
3. 修改版逐次调用的 JIT 实测更快。最终流水线、代码布局等没有逐一控制，不能据此宣传 JIT 或 Mixin 固定提升 15% 性能。
4. 修改版与执行相同修改逻辑的 AOT 版本比较，避免将新增 bonus/分支本身的计算成本误认为变换框架开销。

Windows 默认调度，无核心绑定、无固定 CPU 频率；混合核心、温度和后台负载会影响纳秒级微基准。原始数据保留，后续真实组件需要重新测量。

## 加载、内存和包体

| 项目 | 本次结果 | 口径 |
| --- | --- | --- |
| LLVM DLL 加载和目标初始化 | 3.09～3.44 ms | 每个测量进程第一次加载；OS 文件缓存可能已热 |
| 基础组件解析到机器码可调用 | 4.21～4.34 ms | 已加载 LLVM 后，7 次重复的中位数，各进程范围 |
| 修改组件解析到机器码可调用 | 3.73～4.00 ms | 包含解析、链接、选择、变换、优化、JIT 和符号物化 |
| LLVM-C.dll | 68,580,864 字节，约 65.4 MiB | 当前完整官方 DLL，未定制裁剪 |
| runner exe | 392,704 字节 | 包含测量和 AOT 对照，不是最终引擎集成大小 |
| 两个 bitcode 合计 | 6,044 字节 | 仅本实验数值组件 |
| 工作集，加载前 -> 两个 JIT 可用 | 约 4.5 -> 26.6 MiB | 当前进程快照，增加约 22.1 MiB |
| PrivateUsage，加载前 -> 两个 JIT 可用 | 约 0.6 -> 12.5 MiB | 当前进程私有提交，增加约 11.9 MiB |

基准和重复构建后，即使释放两个保留 JIT，进程工作集约 28.7～28.8 MiB，私有提交约 16.2～16.3 MiB。代码所有者已调用 ORC 释放，但 LLVM、分配器和缓存不会保证马上将全部内存归还操作系统；这些快照不能据此证明或排除长期泄漏。

编译耗时与组件规模、优化和依赖有关。6 KiB 产物的几毫秒不代表完整游戏也只需几毫秒。当前报告不含作者构建时间、下载时间或操作系统冷磁盘时间。

## 已发现的问题和当前处理

最初显式卸载 LLVM DLL 后，程序完成计算和各 JIT 释放，随后在进程退出时访问异常。保留 LLVM DLL 映射到进程结束后，验证、测试和 3 次测量及打包验证均正常退出。

当前采用进程期 LLVM 运行库，单独的 JIT 代码仍按所有者释放。退出依赖的底层原因没有完全审计；不声称支持运行期间卸载 LLVM 本身。这个已知问题保留在后续工程清单中。

## 还没有证明什么

- 没有通用 rustc 驱动生成的源码身份索引；当前依靠实验显式导出的固定 C 符号。
- 没有正式属性宏/SDK/模组包管理；使用两个独立编译的 bc 文件和固定选择器。
- 普通辅助函数等可在保存前被 rustc 的 MIR 优化内联。本例目标调用确实保留，不代表任何源代码调用均可定位。
- 没有堆分配、标准库和第三方 crate 的通用链接、panic 展开、共享静态状态或析构生命周期验证。
- 没有游戏对象跨界借用、任意位置局部捕获或修改后 Rust 安全性证明。
- 没有运行中发布、撤销或多线程代际回收；两个 JIT 并存只是测试对照。
- 没有全游戏性能结论或不可信代码隔离。当前 bitcode 按可信本机代码处理。

## 后续建议

继续方案阶段 B：实现可生成稳定逻辑目标索引的构建集成，以及保留正常 Rust 函数体的属性作者接口；从当前固定实验符号扩展为受约束的直接调用选择器。先把启动时变换做成可用工具，再进入单线程热更新。

当前证据足以支持继续投入这一小步，尚不足以承诺完整 Rust 覆盖面、跨版本兼容或最终性能预算。
