# Rust 运行时 Mixin 方案草案

记录时，阶段 A 已通过，阶段 B 已实现模块宏索引、属性作者接口、独立构建和启动时变换的最小路径。 [阶段 A 历史报告](LLVM_FEASIBILITY_RESULTS.md) · [同日调研报告](../RELATED_WORK.md)

本文提出从现有小型 IR 原型转向复用 rustc/LLVM 的研究路线。独立实验位于 `experiments/llvm-mixin`。现有演示仍按根 README 运行；`modify_call_result` 与有限的 `modify_return_result` 属性已有受限实现，完整用法以 SDK 指南和命令行演示为准；拟议 cargo mixin 命令和 rmod 产物格式仍是设计。本文不把事件系统作为目标。

## 1. 目标和边界

为主动接入专用构建流程的 Rust 程序提供类似 Java Mixin 的代码变换能力：模组用属性选择目标和位置，工具修改目标程序，玩家启动时加载模组，无需修改或重新构建游戏发行程序。

“不重编译游戏”在本文指玩家不运行 Cargo/rustc、不重新生成游戏 exe；运行时仍会对保留的程序表示生成机器码。这一步是 JIT 编译，不能描述成完全没有编译。

基础目标：在目标代码首次执行前应用模组。运行期间的安装、替换、撤销保留为后续目标，不以启动时变换冒充热更新。

第一阶段限定 Windows x64、单线程、纯值函数边界。游戏内部无需为每个修改位置预留事件或 Hook，但必须接入构建工具并将选定代码组件纳入可修改范围。暂不承诺对整个任意 Rust 程序自动生效。

不承诺：跨游戏版本自动适配、跨 rustc/LLVM 版本兼容、修改存活对象布局、修改正在执行的栈帧、对任意引用捕获证明安全、不可信原生模组沙箱。

## 2. 核心决策：复用现有编译器

推荐主线是 rustc 生成可保留的 LLVM bitcode，使用同版本 LLVM 做定位、变换、链接、优化和 JIT。首先做可行性实验，成功后再固定工程架构。

- rustc：处理真实 Rust 语法、类型、泛型实例化和原始函数的借用检查。
- LLVM：处理现成 IR 的链接、验证、优化与机器码生成。
- 本项目：构建集成、目标索引、属性和补丁描述、选择器、受限变换、发布和诊断。

停止以“给自定义表达式语言逐渐补齐 Rust”为主线。当前小型 IR/Cranelift 路线保留为独立验证样例。LLVM bitcode 不能直接交给当前自定义 IR 的 Cranelift JIT；新实验需要单独的 LLVM 执行路径。

MIR 路线暂列替代研究：更接近 Rust 语义，但导出、修改后检查、实例化和重新代码生成依赖更多 rustc 内部能力。主线不可行时先记录原因并评审，不自动转向重写编译器。

## 3. 结构与执行流程

```text
游戏开发者构建
  游戏 Rust 源码
    -> 固定版本的 rustc / 构建集成
    -> 游戏 exe
    -> 可修改组件的基础 bitcode
    -> 函数/调用位置索引、ABI 描述、构建身份

模组作者构建
  正常 Rust 函数 + Mixin 属性
    -> 同套工具链和目标 SDK
    -> 模组处理代码的 bitcode + 补丁描述
    -> 模组包

玩家启动
  游戏读取基础代码和模组包
    -> 检查工具链、基础版本、ABI 和依赖
    -> 从未修改的基础代码定位全部补丁
    -> 链接处理函数、实施变换
    -> LLVM 校验、优化、生成机器码
    -> 一次性发布入口
    -> 开始执行游戏逻辑
```

保留对象是目标平台的编译器产物，不是 Java 那种通用字节码发行承诺。不同平台和架构分别构建。玩家包内包含必要的 LLVM 执行能力；不要求玩家安装 rustc，也不在玩家机器编译 Rust 源码。

第一项实验选择独立的小型 combat 组件。其内部调用统一链接到同一份候选代码；主程序经清晰的入口进入该组件。跨界参数先限定为已验证的数值类型。后续是否自动覆盖整个 crate，要在依赖和 ABI 成立后再扩展。

## 4. 模组作者接口

以下为原方案的接口方向；受限实现已使用 `mixin_sdk::modify_call_result` 和 `mixin_sdk::modify_return_result`，并要求显式 id。属性宏只描述补丁、保留并编译函数体，不再把函数体转换成我们自己的算术表达式树。实际支持范围见 SDK 指南。

```rust
#[mixin::modify_call_result(
    target = "demo::combat::apply_damage",
    callee = "demo::combat::armor_reduce",
    ordinal = 0,
    require_matches = 1
)]
fn adjust_damage(value: f64) -> f64 {
    let bonus = bonus_for(value);
    (value + bonus) * 0.5
}

fn bonus_for(value: f64) -> f64 {
    if value > 10.0 { 3.0 } else { 0.0 }
}
```

普通辅助函数、条件和局部变量由 rustc 编译。初期不是任意依赖都能加载：只验收没有额外宿主依赖的处理代码；标准库、分配、panic、第三方 crate 必须逐项解决链接和运行库问题。

边界类型限制与函数体语言限制分开：第一阶段对外只支持 f64 等少数确定 ABI 的值，但函数体可以使用 rustc 正常支持、且所需依赖已可链接的 Rust。不能把这一点宣传为任意 Rust 模组已完全支持。

构建工具为处理函数生成明确调用约定的桥接入口。桥接可以使用受限的 C ABI；不能依靠导出 Rust 符号或加 no_mangle 就假设 Rust ABI 稳定。

## 5. 位置识别和代码变换

### 5.1 定位

构建工具维护：逻辑函数身份 -> 具体单态化实例 -> LLVM 函数/调用位置。

不以机器地址作为身份，不只依赖源码行号、debug info 或反解 mangled name。索引必须由编译集成产生，并对应实际保存的 bitcode。

首先验证“预期调用在保存点仍然存在”。保存时机须早于会破坏目标结构的优化；仅关闭 LLVM 优化不一定能撤销 rustc 前段已经做的 MIR 变换。具体构建参数、编译器接入点以实验结果为准。

初期只接受可识别的直接调用。泛型多实例、trait 动态分发、间接调用、异步状态机、闭包等没有明确规则时拒绝，不猜测匹配。

### 5.2 第一种变换

```text
原代码：r = armor_reduce(a, b)
新代码：r0 = armor_reduce(a, b)
        r = mod_adjust_damage(r0)
```

保留原调用一次，后续对原结果的使用改为处理函数结果。匹配和类型校验全部完成后才变换。全部模组从不可变基础代码构建，不在上一轮补丁结果上继续累积。

同位置处理函数按确定顺序组合：B(A(original()))。先验证总匹配数量，再按 ordinal 选择；ordinal 是保存版本的代码位置索引，不是执行次数或机器地址。嵌套调用的遍历顺序和输出编号必须由索引格式明确记录。

### 5.3 后续操作

按独立验收推进：

1. MODIFY_CALL_RESULT：修改某次调用的结果。
2. RETURN：修改函数正常返回出口的结果；当前 LLVM 实验已实现 `modify_return_result`，但仅支持 `f64`、显式出口数量和 ordinal。
3. HEAD：在函数体开始前调用处理函数；取消功能另行定义。
4. MODIFY_ARG、REDIRECT：修改调用参数或替换调用，保持明确签名；当前 LLVM 实验已实现单个 `f64` 参数的 `modify_parameter`。
5. OVERWRITE：替换函数实现，明确独占冲突规则。

局部变量捕获、私有字段访问、借用对象传递、Shadow/Accessor 等不包含在首轮。它们需要更完整的 Rust 类型身份、布局、可见性桥接及有效性规则，不能从“能插入一次调用”推导出已经支持。

## 6. 优化和链接

所有目标选择在本轮最终优化之前完成，变换成功后再优化和生成机器码。因此可在修改后允许优化器内联处理函数和目标函数；不能保证优化器一定会内联。

将候选组件和它的内部调用者一起生成，避免调用者内保留旧内联结果。原生宿主不得在可修改入口之外复制一份目标实现继续使用。跨组件调用须通过清楚的发布入口或明确的同代链接关系。

LLVM bitcode 不是完整的可运行世界。必须处理所引用的依赖、数据段、重定位、辅助函数、运行库符号和必要初始化；Windows 的栈探测、异常展开等也需显式验证。不能把“ORC 能运行一个数值函数”扩展为“全部 Rust 程序都能加载”。

工具链固定具体 rustc 身份、配套 LLVM 版本、目标 triple、数据布局、关键 codegen 配置和 SDK 身份。首轮精确匹配，任何不一致明确拒绝。候选代码必须先完成解析、验证、链接和 finalize，才对外发布入口。

## 7. 生命周期和信任边界

原始游戏函数和模组函数都由 rustc 检查，但这不构成变换后整个程序的安全证明。LLVM verifier 校验低层程序结构和类型，不检查 Rust 的全部所有权、别名及语义不变量。

第一轮只连接受限纯值签名，不传指针、引用、拥有堆对象或 Rust 容器。不开放任意局部捕获，不改变对象布局，不插入任意 Drop 操作。这减小验证面，但不能把任意游戏逻辑变换宣传为安全沙箱。

后续对引用和对象类型单独设计：哪些借用由桥接创建、能活多久、哪些变换可验证、哪些需要 unsafe 契约。无法证明的能力必须标明原生代码信任要求，不能以“写的是 Rust”宣称自动安全。

模组代码按可信原生扩展对待。文件格式、哈希和 LLVM 校验不是安全隔离；一般 native handler 可能无限循环、panic，或包含作者自己写的 unsafe。

首轮禁止 panic 跨桥接边界传播；明确选择受限不展开路径并验证运行库约束。如何捕获错误、展开和清理资源属于后续里程碑，不承诺 handler 出错后能够事务式恢复所有副作用。

## 8. 启动应用和运行期热更新

启动应用优先完成：目标组件首次执行前构建并发布候选，不存在正在执行的旧栈帧。

单线程热更新随后实现：只在目标组件调用全部返回后的安全点构建/切换，新一代完整成功后替换入口；失败保留旧代。不重新执行已经完成的逻辑，也不修改活动栈帧。

多线程热更新最后处理：每次进入可修改组件固定一代代码，嵌套内部调用保持同代，旧代在最后一个使用者退出后回收。仅原子替换函数指针无法解决旧代码存活、内联副本、跨代调用或对象析构问题。

“基于原始代码重新生成且失败保留旧代”可以延续现有原型思路，但现有线程局部分发实现不能直接当成全局多线程实现。

## 9. 产物设计

拟议作者命令：cargo mixin build。拟议产物：half-damage.rmod。命令和格式尚未实现。

```text
half-damage.rmod
  manifest.json      # 模组身份、兼容条件、补丁描述、载荷哈希
  handlers.bc        # rustc 生成的处理函数和已收集依赖
  symbols.map        # 本次构建的导出/导入描述（具体编码待定）
```

基础游戏包包含对应基础 bitcode、索引和执行运行库。包只是容器，避免把重命名扩展名当成功能升级。压缩、签名、依赖解析、资源管理都不属于首项可行性实验。

SDK 不能只是复制游戏 crate 的源码后另外编译：必须明确哪些符号来自宿主、哪些被装入候选组件，避免游戏状态、静态变量、运行库重复实例。首轮纯函数组件没有共享全局状态，后续专门验收这项。

## 10. 分阶段实验与验收

### A：工具链和执行可行性闸门

- 独立实验目录，不改当前可运行演示；使用单独固定工具链。
- 找到并记录可用的匹配 LLVM 开发环境、执行 API 和 rustc 产物保存点。
- rustc 编译一个包含普通辅助函数和条件分支的数值组件。
- 在没有 Cargo/rustc 的执行路径中，用 LLVM 加载、链接并执行该产物。
- 比较 AOT 与 JIT 的多组正常/边界输入，记录浮点语义范围。
- 确认目标调用在保存产物中可被稳定识别，并保留对应索引证据。

成功条件：没有自定义 Rust 函数体解释器，真实 rustc 产物被执行，调用结构存在，工具链及依赖可重建。

失败处理：若只能导出不能执行、匹配 LLVM 不可获得、关键调用已不可识别或运行库无法闭合，先给出失败报告；不把它标记为完整接入成功。

### B：一个真正的启动时 Mixin

- 读取基础组件和独立模组 bitcode。
- 根据属性产出的描述定位一次直接调用，插入普通 Rust handler。
- 在最终优化前变换，之后启用优化执行。
- 验证基础值 16，模组通过辅助函数和 if 处理后为 9.5；未修改的独立调用仍为 16。
- 选择器、签名、工具链、基础身份错误均在发布前拒绝。
- 两个同位置补丁顺序明确，原调用不重复，卸除集合重新从基础构建。

成功条件：模组可独立构建；原游戏 exe 不重编译；玩家执行路径不启动 rustc；改的是内部调用位置而不是手写事件；优化构建仍正确。

### C：可用的最小作者流程

- 属性宏保留真实 Rust 函数并生成描述/桥接，不消耗函数体来生成自定义算术 IR。
- 完成可复现作者构建、SDK 身份、包载荷和错误诊断。
- 扩展 RETURN、HEAD，再逐一增加其他操作。
- 普通 helper、受支持依赖与明确签名分别验收；记录未支持项。

### D：单线程热更新

- 游戏同一进程：基础 -> 模组 A -> 模组 B -> 拒绝错误候选并保留 B -> 撤销。
- 仅调用边界切换，验证旧机器码回收和反复更新。
- 一轮最终优化后的依赖调用者与内部调用全部使用同一代。

### E：对象、依赖和多线程

引用/对象桥接、标准库和第三方依赖、panic/析构、状态身份、多线程发布分别设实验。对象布局和栈帧迁移不顺带纳入。

## 11. 性能和交付证据

初期不承诺固定比例的开销。至少记录：正常 AOT、未修改 JIT、修改 JIT 的相同负载；进入组件的调用开销；首次加载和生成耗时；替换耗时；基础和每代代码内存；发布包大小。

同时报告基准代码、工具链、CPU、优化参数和输入，区分持续执行成本与加载成本。保留代码和捆绑 LLVM 会增加包体；影响大小以实际产物为准。

当前 18 个测试覆盖旧自定义 IR 原型，不构成 LLVM 路线已实现或性能已达标的证据。文档评审后建议只先实施阶段 A，再依据实验结果决定阶段 B 的细节。

## 12. 与现有项目的关系

- 现有演示、测试、Cranelift 运行时继续保留，不在本草案中删除或迁移。
- 现有“.mixin.json 中装自定义 IR”是旧验证路径，新路线使用真实编译器产物。
- 指纹检查、从基础重建、匹配计数、补丁顺序、失败保留旧代等设计可以复用。
- 现有 LLVM 无关的代码不直接假装支持新架构。
- 当前 ROADMAP 的“扩展自定义 IR”路线保留为历史计划，主线调整需本方案评审和阶段 A 结果支持。

用户授权继续推进后，阶段 B 最小路径与部分阶段 C 作者工具已经实现并验证，详见 SDK 指南。只有 MODIFY_CALL_RESULT 和当前纯值边界通过验收，不能将完整阶段 C 或热更新阶段标为完成。
